# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Tool name

**UNDERTOW.** The CLI is `undertow` (`prog="undertow"` in `undertow.py`, ASCII banner,
v0.1.0).

## Project overview

Recon automation for authorized external pentest engagements, built stage-by-stage to
mirror the user's real manual methodology (Notion-exported command notes) — not a
generic recon framework. Goal: automate recon and produce a professional,
attack-vector-graded HTML report. Orchestrates external CLI tools via `subprocess`.

**Current state: all 12 stages implemented and validated.** The full Stage 0–12
pipeline is real, working code in `modules/*.py`, orchestrated by `undertow.py`'s
`run_pipeline()`, and was validated against a real external engagement, run
against an isolated scratch copy of its scope files. The design docs/mockups
below are still the authoritative spec the code was built to match:

- **`docs/workflow_v2.html`** — the authoritative pipeline spec. Every stage, every
  tool, every output filename, and the reasoning for every redundant-tool cut.
- **`output/example_report_v2.html`** — the agreed final report design. Multi-tab:
  Dashboard / Attack Vectors / Leaked & Sensitive Data / Recon Detail (collapsible
  `<details>` panels).
- **`output/example_engagement/`** — mock per-stage output directory showing the
  exact file-naming convention the real modules replicate.
- Both were generated by scratchpad Python scripts (not in this repo — they lived in
  the session's scratchpad dir and are gone). The real pipeline is the checked-in
  `modules/*.py` + `report/*`, not regenerated mocks.

## Repo layout

- `undertow.py` — CLI entrypoint (`undertow`). `--check-tools`/`--install` (Stage 0),
  plus `run_pipeline()` which chains all 12 stage modules sequentially. A real run
  auto-creates the engagement folder (named `{client_name}_{YYYYMMDD}` when
  `-C/--client-name` is given, else the bare target) and populates it in the same
  command — no separate `-D` pre-step.
- `modules/` — one module per pipeline stage, all real code:
  - `setup.py` — engagement directory scaffold (`create_engagement()`, called inline
    at the start of a run)
  - `toolcheck.py` — Stage 0 tool registry + installer (covers every tool across all
    12 stages, including the cloned-deps pattern `_install_cloned_py_tool()`)
  - `runner.py` — shared subprocess/file helpers (`run_tool`, `StageResult`,
    `ToolResult`, `read_lines`/`write_lines`/`merge_dedupe`); enforces Rule 1 (only
    write an output file when the tool actually ran)
  - `scope.py` — `Scope` model; in-scope iff (IP in scope.txt OR FQDN matches
    web_scope.txt) AND NOT out-of-scope. Uses stdlib `ipaddress`, not grepcidr.
  - `scope_gate.py` — Stage 3 hard gate, writes `INSCOPE_domain.txt` /
    `INSCOPE_subdomain_ip.txt` / `OUT_OF_SCOPE_domain.txt` (audit-only)
  - `subdomains.py` / `http_probe.py` / `ports.py` — Stage 1 / 2 / 4
  - `web_discovery.py` / `js_analysis.py` / `screenshots.py` — Stage 5 / 6 / 7
  - `cloud_assets.py` / `service_checks.py` / `osint.py` — Stage 8 / 9 / 10
  - `grading.py` — Stage 11 attack-vector scoring
  - `dns_info.py` / `whois_info.py` — leftover from the old generic pipeline, no
    longer called by the real Stage 1–11 pipeline
- `report/` — `generator_v2.py` + `templates/report_v2.html.j2` render the tabbed
  `report.html` per `output/example_report_v2.html`'s design (`generator.py` /
  `report.html.j2` are the old generic single-page report)
- `docs/workflow_v2.html` — pipeline spec, read this first
- `tools/subscraper/` (also `crosslinked/`, `bridgekeeper/`) — cloned deps
  (git-ignored), `.venv/` — their Python deps (Kali blocks system pip installs)
- `output/` — generated reports + example mocks, git-ignored

## Commands

- `undertow --check-tools [--install]` — Stage 0 tool check
- `undertow <target> [-C "Client Name"] [-S scope.txt] [-WS web_scope.txt] [-MD example.com] [-OS out-of-scope.txt] [--vuln-scan] [--js-semgrep] ...` —
  full Stage 0–12 pipeline against a target
- `pip3 install -r requirements.txt`
- No tests/lint/CI exist yet.
- **Directory scaffold is no longer a separate manual step.** The old `-D <name>`
  pre-step is gone. Running the tool against a target auto-creates the engagement
  folder (named for the target) and populates everything inside it in the same run —
  scaffold-then-populate, one command.
- **Scope input flags**:
  - `-S <path>` — `scope.txt` (IP/CIDR)
  - `-WS <path>` — `web_scope.txt` (FQDN suffix)
  - `-MD <domain>` — a bare root domain (e.g. `example.com`) given directly on the
    command line when the client hasn't provided scope files at all; the tool
    writes this into `web_scope.txt` itself (see no-scope-file fallback under rule 3)
  - `-OS <path>` — `out-of-scope.txt`, optional
  - `-C <name>` — client/brand name; drives the engagement folder name and is the
    default for `--cloud-keyword`/`--company-name` when those aren't given separately.
  - Opt-in extras: `--wordlist` (Stage 1 puredns/dnsgen bruteforce), `--vuln-scan`
    (Stage 6/9 nuclei/nikto), `--js-semgrep` (Stage 6), `--ffuf-wordlist` (Stage 5),
    `--shodan-use-cli` (Stage 4), `--github-token` (Stage 1).
  - **At least one of `-S` / `-WS` / `-MD` is required.** If none are given, refuse
    to run — there is no scope to gate on.
  - **Multiple may be combined** — if more than one of `-S`/`-WS`/`-MD` is given,
    the tool unions everything they provide (e.g. `-S scope.txt -MD example.com`
    means both the CIDR file's ranges AND the `-MD` domain's suffix count as
    in-scope).
  - `-OS` is optional and, per rule 2, always wins over an `-S`/`-WS`/`-MD` match
    when there's a conflict.
  - Anything that matches none of `-S`/`-WS`/`-MD` is implicitly out-of-scope by
    default — `-OS` is only for *explicit* exclusions layered on top of an
    otherwise-in-scope match (e.g. carve-outs within an in-scope CIDR/suffix), not
    the only way to be excluded.

## Absolute rules established with the user (do not relitigate these)

1. **One named output file per tool that actually runs.** If subzy runs, there is a
   `subzy.txt`. If sslscan runs, there is an `sslscan.txt`. Never silently fold one
   tool's output into another's file.
2. **Hard scope gate at Stage 3.** Everything from Stage 4 onward reads only from
   `INSCOPE_domain.txt` / `INSCOPE_subdomain_ip.txt`. `OUT_OF_SCOPE_domain.txt` is an
   audit record only — **never read again downstream, absolutely no exceptions.**
   A host counts in-scope if it matches `scope.txt` (IP/CIDR, via `grepcidr`) OR
   `web_scope.txt` (FQDN suffix — catches CDN-fronted hosts), AND does NOT match
   `out-of-scope.txt` (explicit exclusion always wins over a scope match).
3. **Client provides scope, tool never expands it.** `scope.txt`/`web_scope.txt`/
   `out-of-scope.txt` come from the client, dropped into the engagement root by the
   user. Scope-*expansion* techniques (ASN/BGP discovery, reverse-WHOIS, Crunchbase/
   OCCRP acquisition hunting, SSL-SNI cloud-IP scraping) are explicitly excluded from
   the pipeline — they contradict rule 2.
   - **No-scope-file fallback (`-MD`).** Some clients hand over only a root FQDN
     (`example.com` / `*.example.com`) with no `scope.txt`/`web_scope.txt` at all.
     For that case, pass the domain directly with `-MD example.com` instead of
     preparing a file — the tool writes it into `web_scope.txt` itself as the
     suffix-match rule. This is not scope expansion: the FQDN is exactly what the
     client provided, just written into the same gate file the user would otherwise
     drop in by hand. No `scope.txt` (no IP/CIDR gate) gets created from `-MD` alone
     — only `-S` produces that. `out-of-scope.txt`/`-OS` still applies, and still
     always wins, if the client provides one.
4. **Credential/password-spray is manual, out of tool scope entirely** (removed
   Stage 7 early on — user runs CredMaster etc. themselves after getting
   `email/All_Emails.txt` from Stage 10).
5. **Vulnerability-candidate triage ≠ confirmed findings.** `gf`-pattern-matched
   candidates (`Loot/vuln_candidates/{sqli,xss,lfi,ssrf,redirect,idor,rce,ssti,
  debug_logic}.txt`) are for manual verification, never auto-exploited, and never
  shown on the graded Attack Vectors report tab.
6. **Active vuln checks (Stage 9: wpscan, ssl/tls, ssh-audit, ike-scan, subzy,
   socialhunter, clickjack, git-exposure, nuclei/nikto) run last, in-scope only.**
   nuclei/nikto specifically are opt-in behind `--vuln-scan`, never default.
7. **Stage 11 grading sorts most-likely-vulnerable → least-likely** — that ranking
   *is* the report's primary view, not raw counts.

## Tool selection (redundancy already argued through — see docs/workflow_v2.html for full reasoning)

- **Stage 1 passive**: subscraper (`-m all`, covers crt.sh/AlienVault/archive.org/
  VirusTotal/Censys/Shodan/etc in one tool) + amass `-passive` + subfinder +
  urlscan.io + optional github-subdomains. Standalone crt.sh call was dropped
  (redundant, was being queried 3x).
- **Stage 1 active**: amass `-active` + `dnsx -ptr` (reverse DNS over scope.txt
  CIDRs). puredns/dnsgen bruteforce is opt-in only (`--wordlist`).
- **Stage 4 port scan**: naabu + targeted `nmap -sV -p<ports>` + `smap` (Shodan-
  backed, zero-packet) + direct Shodan/InternetDB lookups. **No full `-p-` scan**
  (dropped — too slow for the gain).
- **Stage 5**: katana (crawl) + gau (archive/passive) + arjun (params) + ffuf
  (content discovery) + cariddi. Dropped as redundant: waybackurls/waymore (waymore
  kept as opt-in `--deep-archive` only), gospider/hakrawler (katana already crawls +
  renders JS), gobuster/dirsearch (ffuf is canonical), standalone LinkFinder (jsleak
  covers it).
- **Stage 6 JS analysis** follows the JSRecon methodology (bugbountywriteup Medium
  article) for every CLI-automatable part: `katana -d 5 -jc` + `gau` → merge → dedupe
  → `httpx -mc 200` → `jsleak -s -l -k` (replaces standalone SecretFinder/LinkFinder/
  gf). `trufflehog` kept as an addition (verifies a leaked key is still *live*, which
  jsleak doesn't check). Nuclei credential-disclosure templates gated behind
  `--vuln-scan`. All_js.txt (the list jsleak/trufflehog/semgrep actually scan) has
  known vendor/CDN library JS filtered out first (jquery, bootstrap, react, lodash,
  GA/GTM, etc. — never going to leak an app secret, just wastes scan time); each
  tool's own raw per-tool file stays unfiltered for Rule 1 fidelity.
  **Automatic .map/minified handling (added 2026-10-01, user request)**: before
  trufflehog/semgrep run, every live JS is checked for a recoverable source map
  (`sourceMappingURL` comment, or the `<file>.js.map`/`<file>.min.map` convention)
  — if `sourcesContent` is embedded, the original pre-minification source tree is
  written to `JS/recovered_src/`. Anything left minified with no usable map gets
  `js-beautify`'d into `JS/beautified/` instead. Both directories are passed to
  trufflehog/semgrep as extra scan targets alongside the raw downloaded JS —
  meaningfully better hit-rate than scanning one-line minified bundles directly.
  **Reversal, 2026-10-01**: semgrep was originally dropped here as "wrong tool for
  black-box minified JS" — that reasoning still holds (it's a weak fit on minified/
  no-source-map code), but the user asked for it back explicitly, so it's in as
  `semgrep scan --config auto --verbose`, opt-in behind `--js-semgrep`, additive
  only — never replaces jsleak as the load-bearing secret-finder. LazyEgg (GUI-only,
  not automatable) and manual source-view/browser-extension phases are still dropped.
- **`gf` requires a manual pattern-pack install** — the binary ships with zero
  patterns. `github.com/1ndianl33t/Gf-Patterns` is installed into `~/.gf` on this
  box (14 categories: sqli, xss, lfi, ssrf, redirect, idor, rce, ssti, debug_logic,
  img-traversal, interestingEXT/params/subs, jsvar), and `toolcheck.py`'s registry
  covers it (plus `jsleak` and `smap`) — all resolved.
- **Stage 10 OSINT**: metagoofil/crosslinked/bridgekeeper → `All_Emails.txt`.
  Dehashed was explicitly removed (passive breach lookup dropped per user request).

## Report design notes

- Severity (Critical/High/Medium/Low/Info) maps to the `dataviz` skill's status
  palette (critical/serious/warning/good + muted gray for info — info isn't a real
  status color, just de-emphasized).
- Vuln-type filter chips use the dataviz categorical palette, fixed order, capped at
  8 slots (secret/misconfig/takeover/outdated/tls/access/injection/network) — do not
  add a 9th category without dropping/merging one, per the skill's hard rule.
- **CSS gotcha already hit and fixed once**: define theme tokens on `:root` (and
  `:root[data-theme="dark"]` / the `prefers-color-scheme` media query scoped to
  `:root:where(:not([data-theme="light"]))`), never on a wrapper `<div class=
  "viz-root">`. That div-scoped pattern is for a chart *widget* embedded in a larger
  host page (per the dataviz skill's own example) — using it for a whole standalone
  page broke `<body>`'s background/text color since body sits outside the div in the
  DOM and couldn't see the custom properties.
- Recon Detail tab uses native `<details>`/`<summary>` toggles (expand-all/collapse-
  all buttons) because there's a lot of supporting data — don't flatten it back into
  one long scroll.
- Stage 9 tables have specific user-mandated column shapes — see
  `output/example_report_v2.html`'s "Service / vulnerability checks" panel:
  WPScan (Plugin/Theme, Version, Vulnerable-to), SSL/TLS (IP/FQDN, TLS1.0, TLS1.1),
  IKE (Asset, Hash found?), Subzy (Subdomain, Likelihood %), SocialHunter (Asset,
  Broken link), Clickjack (Asset, Vulnerable Yes/No).

## Stage 7 — Screenshots

EyeWitness over `INSCOPE_domain.txt` (`subdomain/eyewitness/`) + Stage 4's nmap
HTTP(S) services fed as raw nmap XML via `-x` (`nmap/eyewitness/`) — chosen over
gowitness (not installed on this box; EyeWitness's `-x` nmap-XML ingestion and
its screens/source output convention already match setup.py's scaffold for
free). Stage 4's `_run_nmap` now also caches its raw XML output internally
(`nmap/.nmap_raw.xml`, not a Rule-1-visible file) so Stage 7 doesn't re-scan.

**Bug found via real-engagement testing**: EyeWitness does **not** try both
http and https for a bare hostname (no scheme) by default — it only tried
`http://host`, and every one of a VPN-portal-heavy real scope (Citrix/VPN/SFTP
gateways, HTTPS-only) failed as Timeout/BadStatus. Fixed by adding
`--prepend-https` (tries both schemes). Confirmed against real data:
0 → 11/16 successful captures. The remaining 3 timeouts are the same class of
slow-portal issue already seen with jsleak on the client's Citrix gateway — a real
infra characteristic of this client's VPN gateways, not a code gap.

## Stage 8 — Cloud Assets

`cloud_enum -k "<keyword>"` (keyword is a company/brand name — a required
explicit `--cloud-keyword`, never guessed from the domain, since scope.txt/
web_scope.txt don't carry a brand name). "Shodan Karma" dropped — not a real,
verifiable Shodan CLI/API feature (checked `shodan --help` + Shodan's docs;
user confirmed dropping it 2026-10-01 rather than guessing a replacement).
`aws s3 ls --no-sign-request` on any bucket cloud_enum marks `public` is
implemented natively over unauthenticated HTTP instead of shelling out to the
`aws` CLI (not installed on this box, and that's literally all
`--no-sign-request` does). **Two real bugs found/fixed during testing**:
(1) virtual-hosted-style URLs break TLS SNI for any bucket name containing a
dot (e.g. `flaws.cloud.s3.amazonaws.com`) — fixed by extracting the bare
bucket name and always using path-style requests; (2) that extraction regex
itself double-counted the separator dot for the no-region-segment case
(`bucket.s3.amazonaws.com`), silently failing to strip anything — fixed by
making the region segment genuinely optional in the regex. Bucket region is
resolved via the `x-amz-bucket-region` response header (same mechanism
`aws s3 ls --no-sign-request` itself relies on) before the real listing
request, rather than assuming us-east-1.

## Stage 9 — Service / Vulnerability Checks

All 9 checks implemented in `modules/service_checks.py`. Notable decisions:
- Dropped `nmap ssl-enum-ciphers` as redundant with sslscan+testssl.sh (same
  redundant-tool-cut pattern as elsewhere; not a separate file in the mock).
- ssh-audit/sslscan only run against hosts Stage 4's cached nmap XML
  (`nmap/.nmap_raw.xml`) actually shows 22/443/8443 open. ike-scan runs
  against every in-scope IP directly instead — Stage 4 never scans UDP/500,
  so there's no prior "open" signal to gate on for this one.
- wpscan/git-exposure/clickjack/socialhunter/nikto all need a real URL, but
  `alive_domain.txt` doesn't retain which scheme actually responded, so a
  shared `_resolve_base_url()` re-probes https then http per host.
- subzy's real output is binary (VULNERABLE/NOT VULNERABLE), not a confidence
  score — mapped to 100%/0% to satisfy the user-mandated "Likelihood %"
  column shape without fabricating a number subzy doesn't actually produce.
- **Real bug found via testing**: ike-scan's "no IKE service here" signal is
  *not* a literal "No response" string in its output (that never appears) —
  it's the run's summary line (`N returned handshake; M returned notify`).
  Checking for empty stdout was wrong too, since the start/end banner lines
  are always printed regardless of whether anything responded. First pass
  reported a fake positive for `scanme.nmap.org` (zero actual handshakes);
  fixed by parsing the real summary line.
- **Second real bug found via testing**: subzy defaults to plain HTTP and has
  no "try both schemes" mode (`--https` is a single on/off switch, unlike
  EyeWitness's `--prepend-https`) — against the real engagement scope (HTTPS-only
  VPN/Citrix-style hosts, same class of host already seen failing this way
  for jsleak and EyeWitness) this reported `HTTP ERROR` for ~15/16 hosts.
  Fixed by running both an http and an https pass and preferring whichever
  pass actually produced a real verdict per host — went from 15/16 to 3/16
  `http error` (the remainder being the same known-slow hosts already
  isolated elsewhere in this engagement, not a new gap).

## Stage 11 — Grading / Attack Vector Scoring (core deliverable)

`modules/grading.py` reads every graded output file Stages 2–9 may have
produced (never Loot/vuln_candidates/* — rule 5 — and never All_Emails.txt —
rule 4, OSINT feeds the user's manual process, not a vuln) and assigns each
finding a severity + one-line rationale into one of the 8 fixed vtype slots
(secret/misconfig/takeover/outdated/tls/access/injection/network — do not add
a 9th without dropping one, report-design rule). Sorted severity-first, vtype
slot order as a stable tie-break — absolute rule 7. Writes
`attack_vectors.json` (structured, for Stage 12) + `attack_vectors.txt`
(human-readable) to the engagement root.

**Real false-positive bug found via this stage's own real-data validation**
(the bug was actually in Stage 9's git-exposure check, surfaced once grading
synthesized it into a HIGH finding worth double-checking): the check matched
on the substring "HEAD" appearing anywhere in the response body, which
false-positives on any soft-404 app that returns 200 + its normal HTML for
every path (the literal `<head>` tag matched). Confirmed live: a 25KB real
HTML page got flagged as exposed git ref data. Fixed with a strict format
check — a real git HEAD file is tiny and is either `ref: refs/heads/<branch>`
or a bare 40-char SHA1, nothing else qualifies.

## Stage 12 — Report Generation

`report/templates/report_v2.html.j2` + `report/generator_v2.py` render the
agreed tabbed design (`output/example_report_v2.html`) as a single
self-contained `<engagement_root>/report.html` — CSS/JS copied verbatim from
the mock (already dataviz-skill-compliant palette, per the report-design
notes above), body sections converted to Jinja2 loops over real per-stage
data. Screenshots are embedded as base64 data URIs (not referenced by relative
path) so the file is genuinely standalone — real engagement runs are several
MB because of this, which is the correct tradeoff for "must open standalone
for client delivery," not a bug.

**Known, deliberate omission**: the mock also had DNS-records and WHOIS
panels. Those come from `modules/dns_info.py`/`whois_info.py` — the *old*
generic pipeline this project is replacing, which Stage 1-11's real pipeline
never calls. There's no real stage producing that data, so the generator
doesn't fabricate empty panels for it rather than silently dropping it
unflagged.

**Leaked & Sensitive Data tab selection** is broader than the vtype=="secret"
filter chip: per the original workflow spec text, exposed .git and public
cloud buckets belong there too even though their Attack-Vector vtype is
"misconfig" for chip-filtering purposes — handled via an explicit title-based
allowlist in `generator_v2.py`, not a grading.py change (report-level editorial
curation, separate from Stage 11's vtype categorization).

**Validated two ways**: rendered against the mock `example_engagement/` data
and screenshotted via headless chromium (not just a static-file read) — all
4 tabs, filter chips, and collapsible Recon Detail sections confirmed working
visually, matching the mock's design exactly including real (non-mock)
scope-gate reason text, proving genuine data wiring rather than template
fidelity alone. Also rendered and screenshotted against the real engagement
data — 36 real findings, correct stat tiles, correct empty-state handling on
the Leaked tab (no secrets found this engagement, confirmed true per Stage
6/8's own real results).

**Found during this validation** (quality gap, not a functional bug): Stage
11's semgrep grader originally labeled every finding's asset as a generic
"beautified/recovered JS" string. Fixed by tracking semgrep's own file-path
lines as state while parsing its verbose text output, so each finding now
attributes to its actual source file/URL — confirmed against real data.
Residual cosmetic limitation: semgrep's non-TTY verbose output wraps long
local temp-file paths at a fixed width, occasionally truncating the prefix
(e.g. "fied/<hash>.js" instead of "beautified/<hash>.js"); URL-sourced
findings are unaffected. Not worth a second full semgrep invocation with
--json just to fix a label on local-file results.
