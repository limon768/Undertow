Recon Automation — Workflow v2

Original recon methodology. Core rule: everything past Stage 3 touches in-scope assets only.
passive / data gathering scope gate / checkpoint active / vulnerability check (gated, run last) grading (core deliverable) report output

Stage 0 — Setup

undertow.py --check-tools [--install]
Creates directory tree + scope.txt web_scope.txt out-of-scope.txt Note.txt (client-provided scope files)
▼

Stage 1 — Subdomain Enumeration passive + active

1A · Passive sources (parallel)
  • subscraper -m all → subscraper.txt (covers crt.sh, AlienVault OTX, archive.org, VirusTotal, Censys, Shodan, Chaos, CertSpotter, BufferOver, DNSDumpster, BeVigil, RedHunt Labs — 12+ sources in one tool)
  • amass enum -passive → amass_passive.txt
  • subfinder -all → subfinder.txt
  • urlscan.io API query → urlscan_subs.txt
  • github-subdomains optional — needs GH token → github_subs.txt
merge + dedupe → all_passive_domain.txt
1B · Active / brute-force
  • amass enum -active -norecursive → amass_active.txt (handles brute force + permutation + reverse sweep internally)
  • dnsx -ptr over scope.txt CIDRs → reverse_dns.txt (finds hostnames on client's own IP space — not covered by amass)
  • puredns + dnsgen permutation optional — only with --wordlist → bruteforce_domain.txt
merge + dedupe → all_activeScan_domain.txt
1A + 1B merged + deduped → all_domain.txt
Dropped from this stage (redundant or scope-expansion — opinion)
standalone crt.sh curl call — already inside SubScraper's crt.sh module (was being queried 3x).
hakrevdns + prips reverse-DNS sweep — same technique as dnsx -ptr, one tool is enough.
ASN/BGP discovery (Hurricane Electric, asnmap, ARIN/RIPE) — scope-expansion, not needed when the client hands you scope.txt directly.
Reverse WHOIS (whoxy), SSL-SNI cloud-IP scraping (kaeferjaeger) — same reason: finds assets outside the given scope.
Crunchbase / OCCRP acquisition hunting — bug-bounty scope discovery, contradicts "out-of-scope is absolute no."
Google dorking — kept as a manual technique note only, not reliably automatable (CAPTCHA/blocking risk).

Stage 2 — Alive Host + IP Discovery passive probe

httpx -l all_domain.txt -p <expanded port list> -title -sc -ip → alive_domain.txt
grep -i "login|admin" on titles → login_endpoints.txt (metadata, not a separate stage)
▼

Stage 3 — Scope Gate hard checkpoint

  • 3A extract host + IP pairs from alive_domain.txt
  • 3B IP match: grepcidr -f scope.txt
  • 3C FQDN match: suffix check against web_scope.txt (catches CDN/cloud-fronted in-scope hosts whose IP isn't the client's own)
  • 3D exclusion check: drop anything matching out-of-scope.txt, regardless of 3B/3C — explicit exclusion always wins
  • 3E in-scope = (3B OR 3C) AND NOT 3D
→ INSCOPE_domain.txt · INSCOPE_subdomain_ip.txt · OUT_OF_SCOPE_domain.txt (audit record only — never read again downstream)
🔒 locked — everything below reads only from INSCOPE_domain.txt / INSCOPE_subdomain_ip.txt

Stage 4 — Port Scan

  • naabu (fast) → naabu.txt
  • nmap -sV -p<ports> -iL INSCOPE_subdomain_ip.txt → nmap.txt
  • smap (Shodan-backed, zero-packet nmap-compatible output) -iL INSCOPE_subdomain_ip.txt → smap.txt
  • shodan host / InternetDB lookup per in-scope IP → shodan.txt (passive — surfaces ports/CVEs Shodan already indexed, no packets sent to client)
Dropped
nmap -p- full 65535-port pass — too slow/noisy for the gain; targeted port list + naabu + smap/Shodan already covers what matters.

Stage 5 — Web / URL / Param Discovery

  • katana (active crawl, sole default) → Loot/katana.txt
  • gau (Wayback + CommonCrawl + OTX + urlscan, sole default) → Loot/gau.txt
  • merge + dedupe → urls.txt
  • arjun (params, sole default) → Loot/arjun.txt → params.txt
  • ffuf (content discovery, sole default) → dirbrute/ffuf_<host>.txt
  • cariddi → Loot/cariddi.txt
  • WAF + 403 detection on httpx output → nowaf_subs.txt, 403_subs.txt
5.1 · Vulnerability candidate triage (gf patterns) — manual-test checklist, not confirmed findings
  • gf sqli/xss/lfi/ssrf/redirect/idor/rce/ssti against urls.txt + params.txt → one file per class in Loot/vuln_candidates/
Output feeds your manual verification, same as the removed credential-spray step — this tool flags candidates, it does not exploit them.
Dropped (redundant with the tool kept)
waybackurls, waymore — both subsets of/slower than gau; waymore kept as an opt-in --deep-archive flag only.
gospider, hakrawler — katana already crawls + renders JS by default.
gobuster, dirsearch — ffuf kept as the one content-discovery tool.
standalone LinkFinder — jsleak -l (Stage 6) already does this.

Stage 6 — JS Analysis dedicated · JSRecon methodology

  • katana -d 5 -jc | grep .js$ → JS/js_active.txt
  • gau | grep .js$ (passive/archived JS) → JS/js_passive.txt
  • merge + dedupe → JS/all_js.txt
  • httpx -mc 200 → JS/js_live.txt (drop dead links before scanning)
  • jsleak -s -l -k → JS/jsleak.txt (secretFinder + linkFinder + status-code check, one tool)
  • trufflehog filesystem scan on downloaded JS (kept — verifies whether a leaked key is actually still live, jsleak doesn't do this)
  • nuclei credential-disclosure templates opt-in, same gate as Stage 9
Dropped
standalone SecretFinder, LinkFinder, gf aws-keys/github/redirect — all covered by jsleak now.
semgrep — SAST tool for source review, not suited to black-box minified bundles.
LazyEgg browser extension — manual/GUI only, not automatable in this pipeline.

Stage 11 — Grading / Attack Vector Scoring core deliverable

Takes every finding from Stages 4–10 (open ports, WPScan CVEs, JS secrets, exposed .git, weak TLS ciphers, subdomain takeovers, IKE aggressive mode, public cloud buckets, admin panels, missing WAF, etc.) and assigns a severity grade (Critical/High/Medium/Low/Info) + one-line rationale per finding.
Sort order is explicit: most likely to be vulnerable → least likely, top of the list first. This ranking, not raw counts, is what the report leads with.
▼

Stage 12 — Report Generation multi-page, interactive

  • Landing page: stats/summary dashboard (assets found, live hosts, in-scope %, findings by severity, top 10 attack vectors)
  • Attack Vector page: full ranked list, most-likely-vulnerable → least-likely, client-side filter by vuln type (SQLi, XSS, takeover, exposed secret, misconfig, etc.)
  • Leaked/Sensitive Data page: dedicated view of every secret/credential/leak found (JS secrets, exposed .git, cloud buckets, breach data) — surfaced prominently, not buried in raw tool output
  • Per-stage detail pages: subdomains, ports, web, JS, screenshots, OSINT (the sections already built, kept as supporting evidence)
Self-contained HTML + inline JS for filtering (no server, no external CDN — must open standalone for client delivery). Aggregates Stage 11's ranking as the primary view.
